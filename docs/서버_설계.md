# 운행 서버 설계

## 1. 서버가 필요한 이유

페어풀은 **차(Pleos Connect)** 와 **휴대폰 웹** 이 서로 다른 기기라서, 둘이 주고받는 정보는 모두 서버를 거쳐야 합니다. 차 안에서 생기고 차 안에서만 쓰는 정보는 차의 로컬 DB(Room)에 둡니다.

| 데이터 | 저장 위치 | 이유 | 보관 기간 |
|---|---|---|---|
| 운행과 초대 코드(QR) | 서버 | 동승자 휴대폰이 운행 페이지를 열려면 서버에 있어야 함 | 운행 기록으로 남음. 준비 상태로 7일이 지나면 자동 취소 |
| 동승자 탈 곳, 내릴 곳(좌표) | 서버 | 휴대폰에서 입력하고 차가 받아 가서 내비 경유지로 씀 | 정산 때 동네 수준으로 줄이고, **운행 종료 24시간 뒤 삭제**. 도착 정산 화면에서 즐겨찾기에 추가할 수 있도록 정확한 장소(`exact_stops`)도 24시간까지만 남고, 즐겨찾기에 추가하면 그쪽으로 옮긴 뒤 지움 |
| 진행 상황(코스, 남은 시간, 차 위치), 예상 몫 | 서버 | 동승자 페이지 M2, M2-1에 보여 줌 | 정산 때 삭제 |
| 탑승, 하차, 좌석 | 서버(요약) + 차 | 동승자 페이지에 "탔어요, 내렸어요" 표시 | 운행 기록과 함께 |
| 정산 결과 | 서버 + 차 | 시동을 꺼도 동승자 페이지(M3)에 남아야 하고, 즐겨찾기 카풀 월 합계에 씀 | 운행 기록과 함께 |
| 정산 문제 신고 | 서버 | 동승자가 M3에서 남기면 운전자 페이지에 표시 | 운행 기록과 함께 |
| 운전자 계좌번호 | 서버(암호화) | 정산 중인 동승자 페이지(바로 정산 M3, 폴더 정산 페이지 M6)의 "계좌번호 복사". 입력은 차 화면 L1-9(운전자 정보 입력)에서만 | **동의한 경우만 저장**, 차 화면의 "계좌 지우기"를 누르면 즉시 삭제 |
| 운전자 이름, 휴대폰 뒤 4자리 | 서버(뒤 4자리는 운전자별 무작위 값과 섞은 해시) | 운전자가 자기 휴대폰에서 "내 휴대폰으로 보내기" 카드를 열 때 확인. 입력은 차 화면 L1-9에서만 | 운전자가 바꿀 때까지 |
| 내 휴대폰으로 보내기(`share_requests`) | 서버 | 차 화면 L2/P2(초대), L6, L1-7에서 누른 운행이나 폴더 묶음을 운전자 휴대폰에 카드로 보여 줌 | 운행 기록과 함께. 카드는 모두 정산 완료되면 보이지 않고, 정산 요청을 취소하면 지움 |
| 카풀 폴더 | 서버 | 여러 운행의 몫을 쌓아 두었다가 한 번에 정산(M5, M6, M6-1) | 운전자가 지울 때까지. 정산이 끝나면 이름과 동승자는 남고 0원부터 다시 쌓음 |
| 즐겨찾기 카풀(저장된 운행) | 서버 | "지난 운행 다시 만들기"와 동승자가 홈 화면에 둔 고정 링크 | 운전자가 지울 때까지 |
| 동승자 장소 저장 | 서버(즐겨찾기 카풀) | 즐겨찾기 카풀이면 기본으로 남겨 다음 운행에 미리 채움. 동승자가 고른 서비스에 필요한 처리라 따로 동의는 받지 않고 M1에서 미리 알림. 일회성 운행은 남기지 않음 | 운전자가 즐겨찾기에서 x로 지울 때까지(지우는 기능은 운전자에게만 있음) |
| 탑승 기록과 정산 정정 기록 | 서버 | 정산이 완료될 때까지는 지울 수 없고 정정만 가능. 정산을 다시 올리면 이전 결과와 사유를 남김 | 정산 완료 뒤 운전자가 탑승 기록을 지우면 그 동승자의 탑승, 하차 위치와 이름만 지움. 운행, 정산 금액, 정정 내역은 남고 그 몫은 "기록을 지운 동승자"로 표시 |
| 차량 연결 | 서버 + 차 Keystore | 운전자 휴대폰에서 만든 운행을 차가 불러옴 | 차에서 연결을 끊을 때까지 |
| 주행 기록, 연비, 조합별 경로 거리 | 차 | 정산 계산은 차에서 함 | 사용자가 지울 때까지 |

## 2. 계정 없는 신원 확인

| 누구 | 기기에 두는 값 | 서버에 두는 값 | 할 수 있는 일 |
|---|---|---|---|
| 운전자 | 운전자 비밀값(브라우저) | SHA-256 해시 | 운행 준비, 즐겨찾기 카풀, 카풀 폴더 |
| 운행 관리자 | 운행별 관리 비밀값(만든 기기) | 해시 | 동승자 장소 보기, 진행 상황, 탑승, 정산 올리기 |
| 동승자 | 기기 키(브라우저) + 휴대폰 뒤 4자리 | 해시 | 자기 장소 입력과 수정, 정산 결과와 계좌 보기, 다른 휴대폰에서 이어 보기 |
| 차 | 차량 비밀값(Android Keystore) | 해시 | 직접 만든 운행과 연결된 운전자가 만든 운행 관리, 운전자 정보 입력(L1-9: 이름, 휴대폰 뒤 4자리, 정산 받을 계좌. 연결 전이면 차 전용 운전자 행에 두었다가 운전자가 연결하면 그 운전자에게 옮김) |

- 비밀값은 24바이트 무작위 값(hex 48자)입니다. 서버에는 해시만 있어서 DB가 새어도 비밀값을 알 수 없습니다.
- 다른 휴대폰 확인(M1-1, 폴더 정산 페이지)은 이름과 뒤 4자리가 맞을 때만 통과하고, 한 운행(또는 한 정산 페이지)에서 20번 틀리면 막습니다. 틀린 횟수가 오류와 함께 되돌려지지 않도록, 확인 실패는 예외 대신 `{ "error": "verify_failed" }` 로 돌려줍니다.
- 같은 확인 칸에 **운전자**가 차 화면(L1-9)에서 넣은 이름과 뒤 4자리를 넣으면, 동승자 페이지 대신 `{ "driver_view": … }` 로 "내 휴대폰으로 보내기" 카드를 돌려줍니다. 이 화면은 **보기 전용**입니다. 운전자 비밀값이나 관리 비밀값을 주지 않고, 그 휴대폰을 누구와도 묶지 않으며, 바꾸는 함수가 하나도 없습니다. 동승자는 운전자 이름과 번호를 알기 쉬우므로, 고치는 일은 비밀값을 가진 차에서만 합니다.
- 카드는 열어 본 링크의 운행과 그 운행이 속한 폴더 묶음 것만 보입니다. 금액, 구간(동 이름), 계좌가 보이지만 그 링크를 받은 같은 운행, 같은 묶음의 사람들 정보입니다.

## 3. 접근 제어

- 모든 테이블에 Row Level Security를 켜고 정책을 두지 않았습니다. 공개 키(anon key)로는 테이블을 직접 읽거나 쓸 수 없습니다.
- 웹과 차는 `security definer` 함수만 부를 수 있고, 함수 안에서 비밀값 해시를 확인합니다.
- 동승자용 `get_trip` 은 다른 동승자의 장소와 운전자 목적지를 돌려주지 않습니다. 코스는 "동승자 1명 내림"처럼 가리고, 자기 내릴 곳은 동네 이름으로만 보여 줍니다. 차 위치는 그 동승자가 타기 전까지만 돌려줍니다.
- 운전자 계좌는 pgcrypto(`pgp_sym_encrypt`)로 암호화해 저장합니다. 키는 API로 열리지 않는 `private` 스키마에 둡니다.
- 계좌는 운전자가 동의했고, 요청한 기기가 실제로 그 운행에 탔고, 그 사람의 정산이 **정산 중**일 때만 돌려줍니다. 바로 정산은 운전자가 "정산 완료"를 누르기 전까지, 카풀 폴더는 운전자가 합쳐서 정산을 요청한 뒤 그 사람 몫을 받았다고 체크하기 전까지입니다. 요청 전(쌓이는 중)이나 정산 완료 뒤에는 보이지 않습니다.
- 동승자가 보낸 장소에 좌표가 없으면 거절합니다(`place_needs_location`). 차가 내비 경유지를 만들려면 좌표가 필요하기 때문입니다.

## 4. 서버 함수

| 함수 | 부르는 곳 | 하는 일 |
|---|---|---|
| `create_driver`, `get_driver`, `update_driver` | 운전자 웹 | 운전자 시작, 내 정보, 이름 |
| `get_bank_account`, `set_bank_account` | 차 | 정산 받을 계좌 보기, 저장(필수 동의), 지우기(`p_consent => false`). 차 비밀값으로만 부를 수 있음 |
| `get_driver_info`, `set_driver_info` | 차 | 운전자 정보 입력(L1-9)의 이름과 휴대폰 뒤 4자리. 차 비밀값으로만 부를 수 있음 |
| `queue_trip_share`, `queue_batch_share` | 차 | 내 휴대폰으로 보내기(L2/P2는 초대, L6는 운행 정산, L1-7은 폴더 묶음). 운전자 휴대폰은 `verify_device`, `verify_settle_page` 로 보기 전용 카드를 받음 |
| `create_trip` | 차, 운전자 웹 | 새 운행 코드와 관리 비밀값 발급(출발지, 목적지, 좌석 수, 나누는 방법, 운전자 몫 포함) |
| `get_trip` | 동승자 웹 | 운행 공개 정보, 내 정보, 가린 코스, 정산 결과, 조건부 계좌 |
| `join_trip`, `verify_device` | 동승자 웹 | 참여와 수정, 다른 휴대폰 확인(동승자 스스로 빠지는 기능은 없음) |
| `remove_passenger` | 차, 운전자 웹 | 탑승 기록 전에 동승자를 운행에서 뺌(차 화면 L2/P2의 x). 들를 곳에서 빠지고 차는 경로 전체 재요청. 탑승 뒤에는 `record_locked` |
| `report_issue` | 동승자 웹 | 정산 문제 신고(동승자 쪽에는 삭제 기능이 없음) |
| `remove_passenger_place` | 차, 운전자 웹 | 탑승 기록 전에만 그 동승자의 장소를 지움. 들를 곳에서 빠지고 즐겨찾기에 남긴 장소도 지워짐. 탑승 뒤 정산 완료 전에는 `record_locked` |
| `delete_ride_record` | 차, 운전자 웹 | 정산 완료(바로 정산은 정산 완료 체크, 폴더는 그 사람 몫 받음) 뒤에만 탑승 기록 삭제. 그 전에는 `settlement_not_done` |
| `get_settle_page`, `verify_settle_page`, `report_settle_issue` | 동승자 웹 | 폴더 묶음의 정산 페이지(자기 몫만), 다른 휴대폰 확인, 정산 문제 신고 |
| `remove_member_place` | 운전자 웹, 차 | 즐겨찾기 화면의 주소 옆 x |
| `get_trip_admin` | 차, 운전자 웹 | 동승자 전체와 탈 곳, 내릴 곳 좌표, 신고 내용 |
| `set_trip_status`, `update_progress`, `mark_passenger`, `post_settlement` | 차 | 출발과 취소, 코스와 예상 몫, 좌석과 탑승, 하차, 정산 결과(다시 올리면 정정으로 기록, `p_reason`) |
| `choose_settlement`, `mark_paid` | 차, 운전자 웹 | 도착 정산(L6)에서 바로 정산 또는 폴더에 쌓기, 바로 정산의 사람별 정산 완료 |
| `list_folders`, `get_folder_admin` | 차, 운전자 웹 | 카풀 폴더 목록과 상태, 쌓인 운행과 사람별 합계 |
| `request_batch`, `cancel_batch_request`, `mark_batch_paid` | 차, 운전자 웹 | 합쳐서 정산하기, 요청 취소, 사람별 정산 완료(모두 받으면 묶음 종료) |
| `save_carpool`, `recreate_trip`, `get_carpool`, `archive_carpool` | 운전자 웹, 차, 동승자 웹 | 즐겨찾기 카풀 저장(도착 정산 화면 L6/P6에서, 정산이 끝난 운행만. 실제로 탄 사람과 장소, 나누는 방법을 저장하고 즉석 동승 운행도 가능. 즐겨찾기에서 불러온 운행은 다시 묻지 않음), 같은 구성으로 새 운행, 고정 링크와 이번 달 합계 |
| `create_vehicle_link`, `claim_vehicle_link`, `get_vehicle_trips`, `revoke_vehicle` | 차, 운전자 웹 | 차량 연결 QR, 연결, 준비된 운행 불러오기, 연결 해제 |
| `purge_old_locations` | pg_cron(매일 03:15) | 끝난 운행의 장소와 코스 삭제, 오래된 준비 운행 취소 |

## 5. 카풀 폴더 (폴더에 쌓아 한 번에 정산)

| 테이블 | 내용 |
|---|---|
| `folders` | 폴더 이름과 주인(운전자 또는 차). 즐겨찾기 카풀은 마지막에 쓴 폴더를 기억해(`carpools.folder_id`) 다음 운행에서 미리 골라 둠 |
| `folder_batches` | 한 번에 정산하는 묶음. `open`(요청 전) → `requested`(정산 중) → `done`(정산 완료) |
| `batch_payments` | 합쳐서 정산을 요청할 때 확정한 사람별 금액과 횟수, 받았는지 |
| `trips.settle_mode`, `trips.batch_id` | 그 운행을 바로 정산했는지, 어느 묶음에 쌓았는지 |

- 운행마다 차가 계산한 몫(`settlements`)을 그대로 쌓고, 사람은 기기 키 해시로 이어 붙입니다. 같은 사람이 여러 운행에 타도 한 줄로 합쳐집니다.
- 폴더에 쌓은 운행은 운행마다 정산 페이지를 만들지 않습니다. 운행 링크에는 자기 운행과 누적 금액만 보입니다(M5).
- "합쳐서 정산하기"를 누르면 묶음마다 정산 페이지 하나(`/s/<코드>`, `folder_batches.code`)가 생깁니다. 모두에게 같은 링크나 QR을 보내도 기기마다 자기가 탄 운행의 내역과 합계만 보이고, 다른 사람 이름과 금액은 나오지 않습니다. 타지 않은 휴대폰은 이름과 뒤 4자리로 확인합니다.
- 정산 중에도 새 운행은 새 묶음에 쌓입니다. 동승자가 최신 운행 링크나 즐겨찾기 고정 링크로 들어와도, 아직 보내지 않은 묶음이 있으면 그 정산 페이지로 넘어갑니다.
- 정산 요청을 취소하면 정산 페이지 코드가 없어지고, 다시 요청하면 새 코드가 생깁니다.
- 이미 정산을 요청한 묶음의 운행은 정산을 다시 올릴 수 없습니다(`batch_locked`). 동승자에게 확정 금액을 알린 뒤라서입니다.
- 정산 요청을 취소하면 묶음이 요청 전으로 돌아가고, 그사이 쌓인 운행도 다시 합쳐집니다.

## 6. 남은 일

- 장소 검색: 지금은 키 없이 쓰는 OSM 검색(Photon)입니다. 국내 장소 정확도를 위해 카카오 로컬 검색을 Supabase Edge Function으로 감싸 교체합니다(API 키를 웹에 넣지 않기 위해).
- 실시간 갱신: 지금은 동승자 페이지가 5초마다 다시 불러옵니다. Supabase Realtime의 broadcast 채널(`trip:<코드>`)로 바꾸면 더 빠르고 요청도 줄어듭니다.
- 지도 경로선: 지금은 동승자 자신의 점(차, 탈 곳, 내릴 곳)만으로 공개 OSRM 서버에서 도로 경로를 받아 그립니다(실패하면 직선). 시연용이라, 실제 서비스에서는 위치가 외부 서버로 나가지 않도록 차가 보낸 경로나 카카오모빌리티 길찾기를 서버 함수로 감싸 바꿉니다.
